## 一、P0 阻塞项（五项，全过才能发）

### P0-1 · 三个 git 仓健康且不分叉

**为什么是 P0**：分叉意味着「本地和远端各有一份别人不知道的改动」，发布时必然互相覆盖。
**2026-10-27 实测就撞到一次**：主仓本地 2 提交 vs 远端 6 提交，同一件分享卡各做一遍。

```powershell
git -C "C:\Users\saucc\Desktop\星火三部曲" fetch origin
git -C "C:\Users\saucc\Desktop\星火三部曲" rev-list --left-right --count HEAD...origin/main
# 期望输出：0	0
```

**三个仓都要查**：
| 仓 | 路径 |
|---|---|
| 介绍页 | `C:\Users\saucc\Desktop\星火三部曲\` |
| 专注Pro | `产品\星火专注Pro\_gitrepo\` |
| PPT deploy | `产品\星火PPT\deploy\网页版\` |

**失败处置**：
- `0  0` → 通过
- `N  0`（本地领先）→ 本地有未推送提交，确认归属后 `git push`
- `0  N`（远端领先）→ `git pull --ff-only`；若不能快进说明分叉
- `N  M`（**双方都有**）→ **分叉，停手**。先 `git log origin/main..HEAD` 和 `HEAD..origin/main` 对比两边内容，**判断哪边是最终版**，不要盲目 merge

**同时查 fsck**：
```powershell
git -C <仓路径> fsck --no-progress
# 期望：无输出 或 仅 dangling 对象（无害）
# 失败：出现 missing / broken link → 该仓对象库损坏，用远端 clone 的 .git 替换
```

### P0-5 · 分享卡图片可访问且**内容是图片**（已定案：方案 B 服务端托管）

> **⚠️ 本节曾是「待确认项」，2026-10-27 18:12 已定案。**
> 定案依据不是原则，是测速数据 —— 见下方「为什么用服务端」。

**当前实现**：
```html
og:image      = http://8.137.60.56:8000/static/social-card.jpg?v=3
twitter:image = 同上
```

**检查方法（两级，缺一不可）**：
```powershell
# 一级：URL 形式
Select-String -Path "...\index.html" -Pattern 'og:image'
#   期望：指向服务端 或 Pages（两者都已裁定可接受，但需 README 已登记）

# 二级：★ 内容必须真的是图片
#   只看 HTTP 200 不够 —— 坏文件同样返回 200 且 content-type: image/jpeg
python tools\check_release.py --online-only
#   期望：[PASS][P0] og:image 内容  JPEG, xxx KB, image/jpeg ✅（magic bytes 正确）
```

**为什么用服务端（不是「觉得更好」，是实测）**：

| 来源 | 三次耗时 | 体积 | 说明 |
|---|---|---|---|
| 自建服务器 | 86 / 58 / 66 ms | 181,103 B | |
| GitHub Pages | 1,099 / 1,171 / 1,385 ms | 84,888 B | 慢约 15 倍 |
| **Pages 取 583 B** | **861 ms** | 583 B | **受控实验：传输时间≈0，861ms 基本全是网络延迟** |

**583 字节那组是关键的受控实验**：Pages 取一个 583 字节的文件，比服务器取 181 KB 还慢 8 倍 ——
**变量已分离干净，慢的是 Pages 的网络链路，不是文件大小。**

**微信抓图有超时限制，1.1–1.4 秒极可能超时。** 这就是当初改指向服务端的真实原因。

**两个必要条件（都已满足）**：
1. **外部依赖已登记** → 根目录 `README.md`（**不是 `_归档/`，那里被 gitignore**）
2. **兜底真的可用** → Pages 那份图**已修复为有效 JPEG（84,888 B / FF D8）**。
   服务器挂了改一行 URL 就能回 Pages，**且拿到的是真图**。
   ⚠️ 在修复前，这个兜底是「改回 Pages 拿到乱码」，等于没有兜底。

**门禁判定**：
```
[PASS][P0] og:image 内容    ← magic bytes 正确，这是硬要求
[FAIL][P1] og:image 主机    ← 裸 IP + HTTP，已接受取舍，每次打 WARN 让人看见
```

**规矩十的应用**：主机项的判据从「裸 IP = P0 阻塞」降为 P1 WARN，
因为**前提变了**（群管理测速改判接受 B）。改判依据已写进脚本注释。

## 七、本清单自己的局限（写清楚，免得被当权威）

1. **只能验「能打开」，不能验「好不好看」** —— 视觉效果必须人眼看，脚本不评。
