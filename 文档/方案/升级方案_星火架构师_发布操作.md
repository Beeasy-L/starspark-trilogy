### ⑤ 回滚能力实测（不是「应该能回滚」，是「回滚了并证明成功」）

**做法：跑现成脚本，不要手写 PowerShell 改真文件。**

```powershell
python "$R\tools\drill_rollback.py"; echo $LASTEXITCODE
#   期望：exit=0
#   B-3 一致样本的恢复机制有效  N/N 复原
#   B-0 包内与当前发布物一致     全部一致
```

**为什么不用手写命令**（三审意见第 3 条，我原稿的错）：
```
✗ 原稿写法：直接对真实 index.html 做 Replace 破坏再恢复
✗ 风险：中途崩溃/断电/写错路径 → 真实发布物被毁，而演练本意是「验证安全」
✓ 现脚本：全程在系统临时目录操作，只【复制】真实文件出去，绝不写回
```
**演练的目的是验证安全，演练本身不能成为风险源。**

**脚本做三项**：
| 项 | 验什么 | 判据 |
|---|---|---|
| A | 单文件破坏→恢复 | 恢复后 SHA256 == 原值 |
| B-0 | 包新鲜度 | 包内文件 == 当前发布物（不一致 → 先 repack） |
| B-3 | **恢复机制有效性** | 一致样本 N/N 复原（**只验包内一致的，过期的不计入**） |
| C | 自检有效性（反证） | 假 JPEG 能被识破，真 JPEG 不误报 |

> **B-0 与 B-3 必须分开**：包过期（他人在施工）不是机制失效。
> 混在一起会得出「回退包不可用」的错误结论——我第一版就混了，误报了一次。

**为什么必须做**：今天已证两次「执行成功 ≠ 状态正确」——`git reset` 成功但仓仍分叉；`VERSION.txt` 写了 hash 但 hash 已失效。**回滚不演练，等于没有回滚。**

## 4. 风险与回滚

### 风险 1：发布当天有人在仓里做不可逆操作（今天已真实发生）

**最坏情况**：历史被重写 + 双方互推，仓分叉，无法确认哪边是最终版。
**今天（10-27 18:29~18:36）真实发生过一次，耗时约 40 分钟才收敛。**

**预防**（写进发布序列，不做就是没防）：
```
发布当天 08:00 起，仓进入「单点操作」状态：
  只有发布执行人可 push；其他人只读
  任何人要 push 必须先喊「占用」并等 60 秒
```

**回滚**：
```powershell
# 若已分叉：
git -C $R fetch origin
git -C $R rev-list --left-right --count HEAD...origin/main   # 若两数都>0 = 分叉
# 先停手，不做任何 push。用「逐文件对账」判定哪边是全的：
git -C $R diff --name-status HEAD origin/main
# 若确认远端是全的 → 重置到远端（本地有独有提交时先存补丁）
git -C $R diff > "$env:TEMP\my_wip.diff"
git -C $R reset --hard origin/main
```
**怎么证明回滚成功**：`git -C $R rev-list --left-right --count HEAD...origin/main` 输出 `0	0`，且 `check_release.py` exit=0。

### 风险 2：介绍页改了但产品没跟上（版本号不同步）

**最坏情况**：访客看到「第一部 V5.0」，实际是 5.1，**宣传与实际不符**。
**当前就有一处**（见 3-④）。

**回滚**：`git revert <本次提交 hash>` 或 `git checkout <上一版 hash> -- index.html`
**怎么证明回滚成功**：`Select-String index.html -Pattern '第一部[^<]*V'` 输出与预期一致。

### 风险 3：门禁全绿但实际坏了（判据失效）

**这是本轮最该防的风险。** 今天已证 6 次「判据指向了会变的东西」：
```
数 Ch*        → 改架构后失效
裸 IP = P0    → 改判后失效
数 Ch*        → 改架构后失效
git status    → 迁移后失效（racy clean）
git hash      → 重写后失效
git diff --stat 在分叉态 → 失真
```

**预防**：本方案新增的版本口径检查，**判据取自「产品代码里的真值」而非「介绍页文案」**——
即使介绍页写错，产品代码仍是对的，两边一比对就能发现。**指向内容，不指向声明。**

**回滚**：无（检查逻辑错不会破坏数据），但**必须记录「哪个判据失效了」**。

### 风险 4：发布当天网络不稳（今天已发生 3 次）

**现象**：`git push` 报 `Connection was reset` / `schannel handshake failed` / `getaddrinfo failed`。
**预防**：**所有 push 前先 `git fetch` 确认 0/0**；网络恢复后重试一次即可。
**回滚**：不需要。**但要注意：网络失败时 `check_release.py` 的线上检查会报 `[SKIP]` 而非 FAIL —— `[SKIP]` 不算通过，必须重跑。**
